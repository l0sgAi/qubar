# @提及 前端对接文档

> 面向前端同学。后端实现见 `docs/notice-design.md`，通知侧渲染/已读/跳转见 `docs/notice-frontend-api.md`。
> @提及 **没有新接口**：选人用现有的「用户搜索」接口，提交时在**发帖/发评论**接口上多带一个数组字段即可。
> 后端**不解析正文**里的 `@用户名`——正文只是展示文本，谁被 @ 完全由前端传的 `mention_user_ids` 决定。

## 一、总览

| 环节 | 接口 | 说明 |
|---|---|---|
| @ 弹窗选人 | `GET /user/search` | 关键词搜索用户，返回 uuid |
| 发帖带提及 | `POST /post/create` + `mention_user_ids` | 复用现有发帖接口 |
| 评论/回复带提及 | `POST /comment/create` + `mention_user_ids` | 复用现有评论接口 |
| 被 @ 的人收通知 | （无需对接） | 自动进消息中心，type=6，见 `notice-frontend-api.md` |

- 统一响应信封：`{code, message, data}`，下文只描述 `data` 部分。
- `/user/search` 访客可读；发帖/评论接口需登录（原有鉴权不变）。

## 二、@ 弹窗选人：`GET /user/search`

输入 `@` 后弹候选列表，用户输入关键词时调用此接口搜索。

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `keyword` | string | 否 | 搜索词，匹配 username（权重高）和 email。**空串 = 返回全部用户**（按注册时间倒序），可用于弹窗初始列表 |
| `size` | int | 否 | 每页条数，≤0 或 >100 按 20 处理。弹窗场景建议 10-20 |
| `search_after` | string | 否 | 上一页响应里的 `search_after` 原样带回，**JSON 字符串需 URL encode**；首页不传 |
| `circle_id` | string | 否 | 圈子作用域（2026-08-31 新增）。**在圈子内 @选人时必传**当前圈子的 uuid：普通用户 + 全局机器人 + **本圈机器人**可见，**其他圈子的机器人被排除**。不传 = 全站搜索（所有圈内机器人一律不可见）。传非法 uuid 返回 400 |

请求示例：

```
GET /user/search?keyword=小明&size=10
GET /user/search?keyword=小明&size=10&search_after=%5B%220192a1b2-...%22%5D
GET /user/search?keyword=小助&size=10&circle_id=0192c3d4-...   ← 圈内发帖/评论 @选人
```

响应 `data`：

```json
{
  "total": 42,
  "size": 10,
  "search_after": "[\"0192a1b2-...\"]",
  "data": [
    {
      "id": "0192a1b2-...",
      "username": "小明",
      "email": "xiaoming@example.com",
      "avatar_url": "https://...",
      "gender": 1,
      "role": 0,
      "create_time": "2026-01-01 10:00:00"
    }
  ]
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `data[].id` | **用户 uuid，就是提交时要放进 `mention_user_ids` 的值** |
| `data[].username` / `avatar_url` | 弹窗列表项展示用 |
| `data[].role` | 0=普通用户 1=管理员 2=机器人。机器人也可被 @（通知正常落库），是否展示由产品决定 |
| `search_after` | 分页游标。**空串 = 没有更多**；非空则原样带入下一页，**不要自行解析/拼接** |

分页方式（弹窗内加载更多）：

```text
第一页: GET /user/search?keyword=xx&size=10
后续页: GET /user/search?keyword=xx&size=10&search_after=<上一页响应的 search_after>
结束:   响应 search_after === ""
```

注意：

1. 只返回**未删除、状态正常**的用户（后端已过滤，前端无需处理）。
2. 切关键词必须重置 `search_after` 重新拉。
3. 弹窗输入建议**防抖 300ms**；关键词为空时可直接请求空 keyword 拿推荐列表，或前端自己展示「最近互动」等本地数据。
4. `search_after` 排序依据是相关度+id，深翻页时顺序稳定，不会重复/漏数据。
5. **圈内机器人可见范围**（2026-08-31 起）：圈子级机器人（`circle/agent` 创建）只在**本圈内**可被 @——圈内发帖/评论的 @ 弹窗必须带 `circle_id`（取当前帖子的圈子）；全站搜索页不传 `circle_id`，所有圈内机器人均不可见。即使绕过弹窗手搓 uuid 提交，后端发帖/评论时也会静默剔除越圈机器人（不报错、不通知）。

## 三、提交时携带提及

在既有接口上各加一个可选字段：

| 接口 | 新字段 | 类型 | 说明 |
|---|---|---|---|
| `POST /post/create` | `mention_user_ids` | `string[]` | 被 @ 用户的 uuid 列表，接口层最多收 50 个 |
| `POST /comment/create` | `mention_user_ids` | `string[]` | 同上（顶层评论和回复都支持，字段位置不变） |

请求示例（评论）：

```json
{
  "post_id": "0192b...",
  "content": "@小明 说得好",
  "mention_user_ids": ["0192a1b2-..."]
}
```

请求示例（发帖，其余字段照旧）：

```json
{
  "circle_id": "0192c...",
  "title": "周末骑行召集",
  "content": "@小明 @小红 一起来",
  "mention_user_ids": ["0192a1b2-...", "0192d4e5-..."]
}
```

规则与注意（重要）：

1. **前端选人，传 uuid**：正文里的 `@小明` 只是文本，后端完全不解析。用户选中谁，就把谁的 `id` 放进数组。
2. **正文与数组的一致性由前端保证**：用户删掉了正文里的 `@小明`，记得同步从数组里移除对应 uuid，否则被删的人仍会收到通知。
3. **数量上限**：单条最多**生效 10 人**，超出部分后端静默截断（接口层允许传 50）。建议选人 UI 直接限制 10 人并提示。
4. **后端静默过滤**：重复 ID、@自己、不存在/已注销的用户都会被静默剔除，**不报错**；只有值不是合法 uuid 才会 400（`Invalid mention user id: xxx`）。即：传了脏数据不会发帖失败，只是对应的人收不到通知。
5. **可传可不传**：不传或空数组 = 无提及，行为与旧版完全一致，老客户端不受影响。
6. **仅已发布才发**：发帖状态由服务端决定，请求体里的 `status` 会被忽略（旧前端照传不报错）。当前新帖一律直接发布，带提及即触发通知；当前版本没有草稿功能，审核流上线后审核中的帖子不产生提及通知。
7. **mention 优先**：同一用户对同一评论既被回复又被 @ 时，只收到 **@提及** 一条通知，不会收两条。
8. **编辑不补发**：编辑已发布的帖子/评论时新增的 @ **不会**触发通知（当前版本无编辑接口，此条为预留说明）。

## 四、正文展示建议

- 正文里的 `@用户名` 建议渲染为高亮/可点击样式，点击跳用户主页（`/user/detail/:id`，用选人时拿到的 uuid）。
- 后端对正文只做安全清洗（剔除非法 UTF-8/NULL 字节），**不改写 @ 文本**，前端存什么显示什么。
- 用户改名后正文里的旧名字不会自动更新（正文是快照）。若要长期一致的展示，需产品层面定义 mention 结构化存储（当前版本未做）。

## 五、被 @ 方收到的通知

无需前端额外对接，自动进消息中心：

| 项 | 值 |
|---|---|
| `notice_type` | `6` |
| `post_id` | 必有（跳转帖子详情） |
| `comment_id` | 评论/回复中的提及会带（跳详情并定位该评论）；帖子正文提及不带 |
| `snippet` | 评论正文截取（≤100 字符）或帖子标题，直接渲染 |

建议文案：「{actor} 在评论中提到了你：{snippet}」/「{actor} 在帖子《{snippet}》中提到了你」。
列表 Tab 过滤传 `type=6`。详见 `docs/notice-frontend-api.md`。

## 六、行为规则（前端需知的产品逻辑）

1. **延迟**：@ 动作 → 通知可见约 **5 秒**（后端批量聚合落库），属预期。
2. **取消不回收**：发出后删帖/删评论，已产生的提及通知**不会消失**（snippet 快照可读，跳转目标可能 404，前端跳详情需处理目标不存在）。
3. **@自己不通知**：自己 @ 自己不产生通知。
4. **机器人**：被 @ 的是机器人账号（role=2）时通知正常落库；AI 机器人发的评论若 @ 了人，链路一致，前端无感知。

## 七、错误码速查

| 场景 | HTTP | message 示例 |
|---|---|---|
| 未登录调发帖/评论 | 401 | `Token not found` |
| `mention_user_ids` 含非法 uuid | 400 | `Invalid mention user id: xxx` |
| `search_after` 非法 | 400 | `Invalid search_after parameter` |
| 帖子不存在/不可评论 | 4xx | 沿用现有发帖/评论错误语义，无变化 |
