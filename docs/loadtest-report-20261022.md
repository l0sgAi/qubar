# 压测报告 2026-10-22（#63 源站层）

> 环境：阿里云 ECS 单机 4 vCPU / 30G，qubar 镜像 `20f14c51`，全部中间件同机（PG 18 / Redis 8.2 / ES 8.15 heap 2G / Redpanda / Kafka Connect）。
> 方式：k6 v2.3.0 容器加入 `qubar-net` 直打 `qubar:8888`（不经 Cloudflare），`--cpus=1`（实测占用约 0.2 核）。
> 脚本与复现步骤见 `loadtest/README.md`；原始结果在服务器 `/root/qubar-loadtest/results/`。

## 结论

| 场景 | 拐点 RPS | 拐点内 p95 | 越过拐点后 | 首个瓶颈 |
|---|---|---|---|---|
| 读（推荐 / 热门 / 搜索 / 详情 / 评论混合） | **≈ 750** | 5 ms | p95 2.4 s，错误率 0 | 主机 CPU 打满（qubar 1.5 核 + PG 0.8–1 核 + ES 0.6 核） |
| 写（点赞 / 收藏 / 评论 / 发帖） | **≈ 1250** | 12 ms（1250 时 203 ms） | p95 1.3 s，错误率 0 | 主机 CPU；PG 1.6 核、连接池打满 100 |
| 混合（读 90% + 写 10%） | **≈ 600** | 13 ms | p95 3.4 s，**错误率 1–1.6%** | ES CPU 打满 → 搜索线程池拒绝（429）→ 应用返回 500 |
| 浸泡：混合 420 RPS（拐点 70%）× 1 h | — | 11–12 ms | 全程稳定，错误率 0 | 无泄漏；**发现计数批量落库死锁**（见发现 1） |
| 突刺：混合 180 → 900 → 180 RPS | — | 11 ms | 峰值 p95 3.6 s、错误率 3.8% | 同混合；回落后 30 s 内恢复，无残留 |
| 长连：1000 条 SSE（200 用户 × 5） | — | — | 全部建立，0 拒绝 | qubar CPU ≈ 0.5%、内存 +35 MB，长连不是瓶颈 |

- SLO（读 p95 < 300 ms，写 p95 < 500 ms，错误率 < 1%）在拐点以内全部满足，余量很大（p95 个位数到十几毫秒）；
  拐点之后不是逐步变慢而是排队雪崩：所有接口 p95 同时升到秒级，说明瓶颈是共享资源（CPU），不是某个慢接口。
- 单机 4 核是硬上限：拐点处主机 CPU 97–99%，qubar 只用到 1.3–1.5 核（未限 CPU），其余被 PG、ES、CDC 分走。
- 内存、连接、Redis 都不是瓶颈：qubar 峰值 425 MB（限额 2G，`GOMEMLIMIT` 未触发），Redis 峰值 59 MB / CPU ≤ 18%，
  ES heap 52%、无 old GC；PG 连接只在越过拐点后才打满应用池上限 100（PG `max_connections` 200 未触及）。

## 发现与调优建议（按收益排序）

1. **帖子计数批量落库死锁（`40P01`）**。浸泡 1 h 内帖子统计消费者 4 次 flush 失败 3 次（"will retry"，数据合并回缓冲，
   最终 13:08 一次成功，未丢数据）。原因：`post_flush_interval` 15 min 是 `post_hot_flush_interval` 3 min 的整数倍、
   两者 ticker 同时启动，**每次统计 flush 都与热度 flush 撞在同一毫秒**；两者都用 `jsonb_to_recordset` 批量
   `UPDATE domains.post`，行顺序来自 Go map 遍历（随机），再叠加评论同步 `comment_count+1` 与点赞 / 收藏 flush，加锁顺序互相交叉。
   死锁窗口内评论创建等锁最长 0.9 s。
   - 批量 UPDATE 前按 `post_id` 排序（或 `SELECT ... ORDER BY id FOR UPDATE` 再更新），保证全局一致的加锁顺序；
   - 各消费者 flush 间隔错开（加随机抖动），避免整点对齐。
2. **ES 是混合流量的第一瓶颈，且过载时返回 500**（混合场景错误率 1–1.6% 的全部来源）。
   搜索请求与 CDC 重建索引共用 ES 的 CPU；单机下 ES 越过 1 核后，搜索线程池排满开始拒绝。
   - 应用侧：ES 429 映射为 503 / 降级（热门 / 最新流可回落 Redis 候选池或短 TTL 缓存），不要 500。
   - 减少无意义的重建索引（见 3），这是 ES CPU 的大头。
   - 热门 / 最新 / 热榜第一页可加秒级本地缓存（所有人看到的结果相同）。
3. **计数更新写在被 CDC 同步的 `post` 行上，放大 WAL 与 ES 重建索引**。写场景 2.9 万次发帖对应 76 万次 `post` 行更新：
   评论创建同步执行 `UPDATE post SET comment_count+1`（每条评论一次，热帖会形成热点行），点赞 / 收藏 / 热度 / 浏览数消费者
   周期性批量更新；每次更新都经 Debezium 触发整篇帖子重新索引。WAL 复制槽积压峰值 540 MB。
   - `comment_count` 改为与 like / collect 一致的批量聚合；
   - 计数类列拆到不进 CDC 的独立表（或 ES sink 忽略仅计数变化的事件），ES 中的计数改为定时批量同步。
4. **点赞 / 收藏状态批查没有负缓存**（`post/application/service.go` `resolveInteraction`）：ZSET 只存"已赞 / 已收藏"，
   未命中即回源 PG `... AND post_id IN (...)`，而信息流里绝大多数帖子都是"未赞未收藏"，所以每次渲染 20 条帖子都要打两条 PG 查询。
   这是纯读场景 PG 占 0.8–1 核的主要原因。建议首次回源时把该用户的全部点赞 / 收藏装入 ZSET 并打"已完整加载"标记，之后缺失即为 false。
5. **登录态每请求约 20 次额外 Redis 操作**：`RequireLogin` / `OptionalLogin` 先 `IsLogin` 再 `GetLoginID`，sa-token 每次都触发续期
   （GET + SET KEEPTTL + 多次 EXPIRE + session GET）。建议只调一次、续期加节流（如剩余 TTL 低于阈值才续），可省下约 40% 的 Redis 操作与部分 qubar CPU。
6. **SSE 断线检测滞后**（`pkg/composition/notice_stream.go`）：循环只在写入（推送 / 25 s 心跳）失败时退出，不监听连接关闭；
   客户端断线后旧连接最多再占名额 25 s。浏览器网络抖动重连时若已有 5 个标签页，会收到 429，而 `EventSource` 对非 200 不再重连，
   该页实时通知静默失效。建议监听连接关闭（或缩短心跳），并让超限返回可重试的状态 / 踢掉最旧连接。
7. **Redis 帖子统计缓存 like_count 低于 PG**：推测原因（未逐条验证）：缓存过期后由 PG 回填，而点赞先改 Redis、10 s 后才批量落库，
   回填时 PG 尚未包含窗口内的点赞，缓存就永久少计（直到再次过期）。与已关闭的 #46 同类，压测下仍可复现。
8. **容量规划**：当前单机读 ≈ 750 RPS、写 ≈ 1250 RPS、混合 ≈ 600 RPS。qubar 本身只占 1.3–1.5 核，扩容优先把 ES（或 PG）
   拆到独立机器，而不是加 qubar 副本；在此之前做 1–5 项可直接提升单机拐点。
9. 已确认不是瓶颈：Redis `pool_size 10`（Redis CPU ≤ 18%，未观察到阻塞客户端，但未直接测连接池等待时间）、
   qubar 内存（峰值 425 MB / 2G）、Redis `maxmemory 1gb`（峰值 59 MB）、ES heap（52%，无 old GC）、
   PG `max_connections 200`（应用池上限 100，仅越过拐点后打满）。小表（`circle` 17 行、`post_mention` 13 行）的顺序扫描是规划器正常选择，非缺索引。
